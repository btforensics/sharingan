The Sharingan Triage Workflow

A static-analysis pipeline that fingerprints a Windows sample with nine tools, then hands the artifacts to an analyst agent that reasons across all of them and writes the report — start to finish in one command.

1 command, end to end 14-stage pipeline + auto-escalated deep stages static only — never executed output: analysis_report.html

Start here

The one command

From the project root in Claude Code, point the skill at a sample. It collects the artifacts (runs triage.sh for you) and then analyzes them:

> /analyze-sample samples/Ransomware.exe # 1. runs the full triage pipeline → reports/Ransomware.exe_20260626_092953/ # 2. reads every artifact size-aware (mines the big ones), reasons across them # 3. auto-escalates --unpack / --deep (one at a time) when the evidence warrants # 4. writes analysis_report.md, then auto-generates analysis_report.html (the deliverable) ✓ analysis_report.html saved to the report directory (.md source kept alongside)

Call /analyze-sample with no argument and it lists the files in samples/ and asks which one to analyze — it never auto-picks.

Host resources

System requirements & staying within limits

Triage is resource-hungry in two distinct places, and each has its own failure mode if the host is under-provisioned. Size the box for the heavy stages, and the pipeline runs crash-free.

ResourceMinimumRecommendedWhy it matters
RAM8 GB16 GBGhidra (--deep) is a JVM wanting a multi-GB heap; Speakeasy (--unpack) emulates a full PE in memory; floss+capa are memory-heavy even in a base run. Below 8 GB the Linux OOM-killer terminates a process mid-run.
vCPU24capa and Ghidra analysis are CPU-bound; 4 cores keep base triage to a few minutes.
Swap2 GB4–8 GBA safety net, not speed: under a memory spike the kernel pages to swap (slow) instead of OOM-killing (a hard crash). Worth having even at 16 GB.
Disk20 GB40 GB+Ghidra projects, carved unpacked/ payloads, and the report dirs accumulate.
Java (JDK)2121Only for --deep; Ghidra 12.1.2 is pinned to JDK 21 by its installer.

Two crash modes — and how the skill avoids each.

1 · Out-of-memory (the process dies). Caused by stacking the heavy stages. The skill runs them one at a time, never together — separate triage.sh invocations, --unpack before --deep — so an 8 GB host comfortably handles base triage plus one heavy stage. More RAM (not swap) is the real fix; swap just turns a hard kill into a slowdown.

2 · Context-window exhaustion (the analysis dies). Independent of RAM — caused by the analyst reading huge artifacts verbatim (floss.json ≈ 800 KB, capa.json ≈ 400 KB, a multi-child archive report > 9 MB). The skill now reads size-aware: small artifacts in full, large ones mined with Python for just their relevant fields, and archive children processed one at a time. Every artifact is still accounted for — the big ones are mined, not dumped.

Rule of thumb on this box. Analyze one sample at a time, let each run finish before starting the next, and don't manually fire --deep and --unpack in the same command. The skill already enforces this when you use /analyze-sample; it only matters if you drive triage.sh by hand.

What runs, in order

The collection pipeline

This is what ./triage.sh <sample> executes. It is no longer a fixed line — a routing front door (stage 1) identifies the file type, then the universal stages run on every sample while the format-routed stages run only what fits. For a PE that is 14 always-on stages (shown below) plus two deep stages (--deep, --unpack) that the skill now auto-escalates when the evidence warrants — see Going deeper for the trigger rules. Non-PE samples (Office / PDF / LNK / archive / email) skip the binary block and route to tools/nonpe.py instead. Each stage writes one artifact into the timestamped report dir; floss and capa are the slow ones (minutes).

1

Identify & route — the front door

identify.py · magic + file + extension

Classifies the input (PE / .NET / ELF / Office / PDF / LNK / script / archive / email / unknown) and flags extension↔content mismatch (masquerade, e.g. PE bytes named invoice.pdf). This verdict decides which routed stages run — every later stage keys off it.

$ python3 "$IDENTIFY" "$SAMPLE" "$REPORT_DIR/fileinfo.json"
→ fileinfo.json  · read this first
2

Hashing & fingerprint

md5sum · sha1sum · sha256sum

Computes the identity of the sample. The SHA-256 becomes the lookup key for every reputation service downstream.

$ sha256sum "$SAMPLE"
→ hashes.json
3

VirusTotal lookup

curl · VT API v3

Pulls multi-engine verdicts, the suggested threat label, crowdsourced YARA, TrID, and PE metadata. Your strongest single signal for family attribution.

$ curl -s --url \ "https://www.virustotal.com/api/v3/files/$SHA256" \ --header "x-apikey: $VT_API_KEY"
→ virustotal.json
4

MalwareBazaar lookup

curl · abuse.ch

Checks whether the hash is a known, shared sample — and if so, its community family signature and tags. A hit lets you pivot on the family immediately.

$ curl -s -X POST --url "https://mb-api.abuse.ch/api/v1/" \ --header "Auth-Key: $BAZAAR_API_KEY" \ --data "query=get_info&hash=$SHA256"
→ malwarebazaar.json
5

Packer / compiler detection — PE/.NET/ELF route

Detect-It-Easy (diec)

Identifies the compiler, linker, and any packer/crypter. Tells you whether you are looking at clean code or something obfuscated before you spend time on it.

$ diec --json "$SAMPLE"
→ die.json
6

PE structure — PE/.NET route

pestats.py

Parses headers, sections (entropy, permissions), the import table, TLS callbacks, digital signature, and — crucially — any high-entropy overlay that hints at a packed payload.

$ python3 "$PESTATS" "$SAMPLE"
→ peinfo.json
7

String extraction & deobfuscation — PE/.NET/ELF route

FLARE FLOSS

Beyond plain strings, FLOSS emulates the binary to recover decoded, stack, and tight strings — surfacing XOR-hidden URLs, domains, registry keys, and file names. The richest artifact, and the one to mine carefully.

$ floss --json "$SAMPLE"
→ floss.json  · slow (minutes)
8

Capability mapping — PE/.NET/ELF route

Mandiant capa

Matches code against a rule set to name concrete capabilities and map them to MITRE ATT&CK. Note: capa sees only what it can disassemble — a packed payload can come back empty, which is itself a finding.

$ capa --rules "$CAPA_RULES" --json "$SAMPLE"
→ capa.json  · slow (minutes)
9

Config / C2 extraction — PE/.NET/ELF route

configextractor-py · CAPE + rat-king parser packs

For a recognized family (AsyncRAT, Remcos, RedLine, QakBot, Lumma, Cobalt Strike, … — 61 parsers) it statically rips the embedded config block: C2 hosts/ports, encryption keys, campaign/botnet IDs, mutex, install paths. These are often AES-encrypted in the binary and so invisible to strings/floss — this is what surfaces them. Not a reputation lookup: per-family parsers decrypt this sample, so the IOCs can be brand-new and feed back into the reputation + pivot stages. no_match is a real result; it also re-runs on the --unpack recovered body.

$ python3 tools/config_extract.py "$SAMPLE" "$REPORT_DIR/config.json"
→ config.json
10

YARA signatures — universal

yara · local + signature-base

Runs your local rules and the Neo23x0 signature-base recursively, flagging known family patterns, packers, and suspicious traits (mutexes, VM-detection, Winsock).

$ yara -r "$YARA_RULES_DIR/yara-rules/index.yar" "$SAMPLE" $ yara -r "$YARA_RULES_DIR/signature-base/index.yml" "$SAMPLE"
→ yara.txt
11

IP reputation — universal

python · AbuseIPDB

Parses floss.json for IP literals, drops private ranges, and checks the first five public IPs against AbuseIPDB. Empty when the sample hides its C2 behind domains rather than hardcoded IPs.

$ python3 # extract public IPs → AbuseIPDB /api/v2/check
→ abuseipdb.json
12

Domain / C2 reputation — universal

python · ThreatFox · URLhaus · VT-domain

Closes AbuseIPDB's blind spot for domain-based C2. Pulls hosts from floss.json (URL-derived hosts first, bare matches filtered for noise) and checks each against ThreatFox (known-IOC + malware family), URLhaus (malware-distribution URLs), and the VirusTotal domains API (verdict + passive-DNS resolutions → real C2 IPs). abuse.ch reuses your unified Auth-Key; VT-domain reuses the VT key.

$ python3 tools/domain_rep.py "$REPORT_DIR/floss.json" "$REPORT_DIR/domain_rep.json"
→ domain_rep.json
13

VirusTotal pivoting — universal (when VT-known)

python · VT API v3 relationships

Expands one sample into its family/campaign. Forward: the sample's own footprint (contacted domains/IPs, dropped files, ITW URLs). Reverse: sibling samples that share an indicator or the same imphash. Paced for the VT public-tier rate limit; gated reverse pivots are captured as a 403, not a crash.

$ python3 tools/vt_pivot.py "$REPORT_DIR/virustotal.json" "$REPORT_DIR/vt_pivot.json"
→ vt_pivot.json
14

Tool & rule-set provenance — universal

python · versions + rule-set commits

Stamps the exact stack that produced the report — each tool's version (capa, floss, die, yara, ghidra, speakeasy, configextractor, python) and each rule-set's git commit + date — bound to the sample hash. Makes every report reproducible and audit-grade. Local-only, runs last.

$ python3 tools/provenance.py "$REPORT_DIR"
→ provenance.json
++

Ghidra deep RE — auto when a code-level question remains, --deep

Ghidra 12.1.2 · headless

Triggered by ./triage.sh <sample> --deep — which the skill fires automatically when a decrypt / loader / C2 routine is worth decompiling (on a packed sample, only after --unpack, pointed at the recovered body). Runs Ghidra's headless analyzer and a Java export script that emits a function inventory, imports, strings, and targeted decompiled C (entry point + functions calling network/crypto/loader APIs — not a full dump). Slow and heavy, so it is off by default. On a packed crypter it sees only the loader stub, not the encrypted overlay.

$ "$GHIDRA_HOME/support/analyzeHeadless" … \ -postScript ExportGhidra.java "$REPORT_DIR/ghidra.json"
→ ghidra.json  · slow (minutes), opt-in
++

Emulation unpacking — auto when the PE looks packed, --unpack · PE only

Mandiant Speakeasy · CPU emulator

Triggered by ./triage.sh <sample> --unpack — which the skill fires automatically when die names a packer or peinfo shows high entropy / a tiny import table / a large overlay. The sandbox-free answer to a packed sample: it emulates only the loader stub in Speakeasy (Windows-API emulation — no VM, no detonation, no network), lets the stub self-decrypt in emulated memory, carves the recovered payload, then re-runs floss / capa / YARA on the real body into an unpacked/ subdir. When the stub bails early (unsupported API, anti-emulation, remote-keyed) it records a gap and points you to a sandbox — it never fakes an unpack. Recovers embedded indicators only (not confirmed-live behaviour).

$ python3 tools/unpack_emulate.py "$SAMPLE" "$REPORT_DIR" "$REPORT_DIR/fileinfo.json" # then floss/capa/yara re-run on the carved payload → unpacked/
→ unpacked.json + unpacked/  · opt-in, PE only

What you get

Reading the output

Everything for one run lives in a single timestamped directory. The JSON/text artifacts are the evidence; analysis_report.md is the analyst's write-up over them, and analysis_report.html is the rendered deliverable.

reports/Ransomware.exe_20260626_092953/ ├─ hashes.json # identity ├─ virustotal.json # multi-engine verdicts + labels ├─ malwarebazaar.json # known-sample family / tags ├─ die.json # compiler & packer ├─ peinfo.json # PE headers, sections, imports, overlay ├─ floss.json # decoded + static strings ├─ capa.json # capabilities → ATT&CK ├─ config.json # extracted family config (C2/keys/mutex) — when a parser matches ├─ yara.txt # signature matches ├─ abuseipdb.json # IP reputation ├─ domain_rep.json # domain/C2 reputation (ThreatFox, URLhaus, VT-domain) ├─ ghidra.json # decompiled funcs (only with --deep) ├─ analysis_report.md # the written analysis (source the HTML is built from) ├─ analysis_report.html # ← the deliverable, auto-generated every run └─ analysis_report.{pdf,docx} # extra formats, on request

What the report always contains

The structure is fixed by CLAUDE.md so every report is comparable:

  • Executive Summary — 3–5 plain-language sentences.
  • Threat Assessment — family, type, confidence, severity.
  • Hypothesis List — each claim with confidence, cited evidence, and a next action.
  • IOC Table — hashes, domains, IPs, registry keys, files, mutexes.
  • ATT&CK TTP List — techniques prioritized by severity.
  • Recommended Next Steps — gaps and how to close them.

How confidence is labelled

Findings are graded, not stated as fact — static analysis proves capability, not behavior:

High confirmed across multiple sources   Medium suggested by one or two   Investigate a lead to chase

The strongest findings cross sources. A capability that shows up in the imports and the decoded strings and a YARA hit is far more credible than any one tool's output alone. The agent is told to weight evidence that corroborates.

The HTML report is generated automatically

The .md is the source of record — written first, always kept. But the deliverable is analysis_report.html, and the skill builds it automatically every run (no prompt) with the bundled cross-platform exporter (Windows / Linux / macOS):

$ python3 .claude/skills/analyze-sample/export_report.py \ reports/<name>_<ts>/analysis_report.md --to html

One dependency: pandoc. The HTML is a self-contained, styled, dark-theme page (CSS embedded — nothing external to load). PDF and DOCX are still available on request (--to pdf / --to docx / --to all); the PDF is pandoc-rendered HTML printed by a headless browser (Edge on Windows, Chrome / Chromium / Brave elsewhere — auto-detected), no LaTeX or weasyprint, and long hashes wrap correctly. Everything lands next to the .md, which is never replaced.

When a sample is packed

Going deeper

The skill now auto-escalates the two deep stages when the base artifacts call for it — you don't pass the flags yourself. After the base run it inspects fileinfo.json, die, and peinfo.json and decides:

Trigger 1 · packed PE

→ auto --unpack

Fires when it's a PE that looks packed: die names a packer, or peinfo shows ~7.0+ section entropy, a very small import table, or a large/high-entropy overlay. Skipped for non-PE types and plainly-unpacked PEs.

Trigger 2 · code-level question

→ auto --deep

Fires when a decrypt / loader / C2 routine is worth reading as code. On a packed sample it runs after --unpack, pointed at the recovered body — never at the loader stub.

Order & sequencing. Unpack before deep (Ghidra on a packed stub only sees the loader). The stages run one at a time, never stacked — each is a separate triage.sh invocation — and the skill tells you before each fires and why (e.g. "die flags UPX + 7.9 entropy → auto-running --unpack"), or notes in one line when one is skipped. On the existing-report-dir / Windows path it can't re-trigger collection, so it recommends the flag as a next step instead.

Once escalated, the deep pass itself proceeds as:

  1. Carve & characterize the overlay (entropy, header bytes, embedded signatures via binwalk).
  2. Try the easy unpack first — upx -t and known-packer checks.
  3. Locate the decryptor in radare2: cross-reference file-read and GetModuleFileNameA calls, then disassemble the candidate functions (cross-checked against FLOSS's decoding-function scores).
  4. Read it as C — with --deep, ghidra.json carries decompiled pseudocode for the loader/decrypt functions, which is faster to reason over than disassembly. (Verified on av45i.exe: it pinned the Protected-Storage credential routine and a process-watchdog respawn thread.)
  5. Recover the algorithm if it is self-contained (e.g. a single-byte XOR) — and dump the cleartext.

Two honest limits. If a payload is keyed at runtime or from C2, static unpacking hits a wall — the report says so plainly rather than inventing a result. And the sample is never executed; confirming dynamic behavior needs an isolated detonation sandbox, which is out of scope for this host.

Operating discipline

Safety & good practice

  • Never run the sample. The whole pipeline is static. Treat files in samples/ as live ordnance.
  • Reputation lookups leave your network. Stages 2, 3, and the IP/domain checks send the hash, extracted IPs, and extracted domains to VirusTotal, MalwareBazaar, AbuseIPDB, and abuse.ch (ThreatFox/URLhaus). Don't submit indicators you need to keep confidential.
  • Guard config.env. It holds live API keys in plaintext — keep it out of version control and shared screenshots.
  • Conclusions are theories. Every claim is graded and cited; confirm the important ones dynamically before you act on them.
